## 0. 结论摘要

**这不是一次「评分看错」，而是四层机制叠加**：

1. **叙事身份错位（入口层）**：天奇是机器人/具身智能票（东财板块含「人形机器人」「机器人概念」，业务为工业具身智能数据采集），却以「动力电池回收」概念身份进入埋伏道。
2. **板块级信号替代个股校验（闸门层）**：埋伏道入场与排序只吃板块 3 日流，个股主力流向、叙事、动量全部不参与；而该概念板流入由非电池票（光华=PCB/电子化学品、杰瑞=AIDC/数据中心）主导。
3. **缺评分数被当满分（评分层）**：埋伏决赛票不跑技术/风险评分，`tech` 被 `ambush_rank_score×100` 顶替，`risk` 取 dataclass 默认 100；`composite 57.8` 中 20 分权重来自默认值。
4. **硬止损优先级最低（持仓层）**：`assess_holding` 的 ①–⑦ 分支任一先命中即丢失 `lifecycle_action`，`-5.31%` 的 `-5%` 硬止损只在分支⑧被执行；10-29 走的是分支②「论点漂移→家族宽限」。

**一句话因果链**：
> 电池板用电池资金（且被异主题资金污染）通过 G-A1 → G-A4 同分取问财序第一（恰好是机器人票）→ 缺评分数撑到 57.8 → 埋伏 lift 47.1→55 + bear 豁免成交 → 次日板块解析漂移触发 thesis 宽限，硬止损未执行。

## 9. B+C 修法设计：分层准入 + 潜在催化源扩充（2026-10-29 拍板方向，未实施）

> 本节只定设计，不改生产代码。B = 把「催化 = 准入硬闸」改为「评分/催化分层排序」；C = 扩充催化事件源，不再只依赖 Node 4 当日 12 条。
> 实施前必须按 §9.6 做离线回放 + shadow；本节结论推翻 2026-08-22 P3「无合格催化 → 蓄水池」的前提，需负责人单独裁决。

### 9.1 证据：池子为什么必然稀疏

64 个归档日扫描（`data/got_daily/2026*`，含 10-29）：

| 指标 | 实测 |
|---|---:|
| Node 4 `major_events` | **12.5 条/日** |
| Node 2 `ambush` 候选 | **11.0 个/日** |
| Node 6 正式池 | **0.56 个/日** |
| 正式池为 0 的天数 | **44/64（69%）** |
| Node 4 事件按名称精确覆盖的 ambush 板块 | **0.27 个/日** |
| 36 条入池记录来源 | 日历 23 / Node 4 6 / 蓄水池升格或提名 7 |

> 口径：逐日读归档 `unified.json` / `sector.json` / `news.json`；板块名用 `normalize_sector_name` 归一化后取精确交集；入池来源按 `gate_notes` 是否含 `Node4事件` / `蓄水池升格` / `Agent提名` 分类。

10-29 当日：13 条 Node 4 事件、16 个 ambush 候选，`affected_sectors` 与候选**精确同名命中 0 个**；唯一入池的水运靠“港口运输”经别名/glue 映射；其余 8 个 `no_catalyst` + 7 个 G4 吸筹否决。

**结构性原因**：

1. Node 4 的目标是“市场级重要性”，不是“板块覆盖”：终审 12 条封顶 + MMR 主题去重，天然偏向已被市场注意的主线（芯片/AI/机器人/政策）。
2. 埋伏按定义是低关注、低位、未上头条的板块；要求它当天有合格新闻，等价于要求“未来的主线现在就上头条”。
3. 催化是硬门槛（`aggregator.py:3438-3465`），不是加分项；`no_catalyst` 直接出池。
4. 日历叙事只读 Node 4 的 `news_events`（`catalyst_calendar.py:872-906`，候选上限 30），12 条短名单之外的原始新闻不进入抽取；跨日发酵虽已由 `_format_fermenting_section` 注入叙事 prompt（`catalyst_calendar.py:780-804`，2026-10-22），但只作为 LLM 输入，**没有落成板块级催化候选**。
5. 名称映射又砍一层：10-29 精确同名命中 0，说明 alias/glue 只能兜底，救不了覆盖面。

### 9.2 B：三层准入 + 分层排序

#### 信号定义

- **S（评分）**：Node 2 `ambush_score_v2`；`S_pass = Track1（state=ambush）或 score ≥ AMBUSH_SCORE_FLOOR(0.30)`。
- **C（催化）**：合格催化；T1 口径 = 日历 `confidence≥0.6` 非负面，或 Node 4 `impact∈{high,medium}` 非负面；T3 口径更严（见 §9.3）。
- **G（闸门）**：G1 利空 / G2 防买顶 / G3 拥挤度 继续硬否决；G4 吸筹仍是必要条件（净流出不成 T1/T2；T3 必须 G4 通过，不允许 `missing` 放行）。

#### 准入矩阵

| Tier | S | C | 入池 | 基准系数 | 说明 |
|---|:--:|:--:|:--:|---:|---|
| **T1 评分+催化** | ✅ | ✅ | ✅ | 1.0 | 现有行为；最高优先级 |
| **T2 单评分** | ✅ | ❌ | ✅ | 0.7 | 原 `no_catalyst` 不再出池，降级入池 |
| **T3 单催化** | ❌ | ✅（强） | ✅（限 2/日） | 0.5 | 补过通道；仅强催化 + G4 通过 |
| 无 | ❌ | ❌ | ❌ | 0 | 蓄水池（`near_miss` / `no_catalyst`） |

- `S_pass` 的 Track1 成员即使分数低于 0.30 也算 S 过（状态机权威），与原双轨口径一致。
- T3 的 S 为 `score < 0.30` 且不在 Track1；这是“评分没过、催化补过”的显式通道。
- 排序键：**先 Tier，后组内分**——T1 > T2 > T3；T1 内按 `wS×S_norm + wC×C_norm`，T2 内按 S，T3 内按 C。这样严格执行「评分+催化 > 单评分 > 单催化」。
- 正式池上限仍为 `CATALYST_MAX_POOL_SIZE=10`；T3 另设 `T3_MAX=2/日`，防止弱候选挤占 T1。
- 蓄水池 `reason` 语义收紧：`no_catalyst` 只在 S 与 C 都不满足时使用；S 过、C 空 → 直接 T2，不再写 `no_catalyst`。

#### 审计与下游

- `AmbushCandidate` 新增：`admission_tier`（T1/T2/T3）、`admission_score`（S）、`catalyst_score`（C）、`catalyst_source`、`catalyst_event_id`；`gate_notes` 保留原闸门文本。
- `SectorIntel` 新增 `ambush_tier`；T1/T2/T3 均可为 `actionable`，但 Phase 2 基准仓位乘 Tier 系数（1.0/0.7/0.5），T3 另受 2 只上限约束。
- 这样不改变 `classification` 的现有语义，避免下游再次出现“池内但 caution”的二义性。

## 10. 催化剂日历重复输出：事件身份设计缺陷（2026-10-29 新增）

### 10.1 现象与证据

10-29 归档 `data/got_daily/20261029/news.json` 共 22 条事件：

| 现象 | 归档事实 |
|---|---|
| 今日 5 条同题 | `[全球] OpenAI/Google/Meta 发布会`，同一 `event_date=2026-10-29`、同一 `source=global_map`，仅 `sector` 不同：AI应用 / 文化传媒 / 传媒娱乐 / 网络游戏 / 短剧游戏；`event_id` 各不相同 |
| HBM 两条同板块 | `event_date=2026-11-04 / 11-05`，均 `sector=HBM概念`、`source=llm_narrative`、`confidence=0.62`，`source_news` **完全相同**（三星电子 HBM4E 量产表态），标题仅措辞差异 |
| 跨日持续 | OpenAI 5 条在 10-28 / 10-29 两次归档中 `event_id` 完全相同；HBM 在 10-23 / 10-26 为 11-03，10-29 变为 11-04 / 11-05 |

### 10.2 根因：逻辑事件身份与行身份被压成一个 ID

- `_make_event_id = MD5(source|event_type|sector|date)`（`catalyst_calendar.py:132-134`）把逻辑事件、板块、日期压进同一个键。
- `_deduplicate` 的去重键是 `(sector, event_date)`（`:1806-1813`），只能合并同板块同日：全球事件每板块一行、叙事同一事实每日期一行都会存活。
- `global_map` 按命中板块逐行生成（`:688-704`），所以“今日 5 条”本质是**一个事件的板块扇出**，不是 5 个独立事件；`catalyst_identities` 只覆盖 `global_event`，用于锁定首次 `catalyst_date`（`storage.py:1210-1225`）。
- `llm_narrative` 在解析时按 `sector + date` 生成 `event_id`（`:1097-1109`），没有叙事身份表；增量更新只跳过相同 `event_id`（`:487-505`），日期一变就是新事件。
- 因此两类现象要分开处理：**全球 5 条是扇出 + 展示未聚合；HBM 两条是真重复 + 无同源跨日去重。**

### 10.3 影响

- 今日 8 个展示位被 1 个全球事件占 5 格，标题写“5 个事件”，逻辑上只有 1 个。
- HBM 两条同板块事件均过 `CATALYST_CONFIDENCE_GATE_LOW=0.6`；若 HBM 进入埋伏评分，`_compute_catalyst_score` 会把第二条计入冗余，主催化分 **+20%**（`aggregator.py:4344-4351`）。
- 两条 HBM 各注册一条 P6 记录（`register_event` 按 `event_id`），P6 样本相关且重复；`板块催化密度` 也显示 2 个事件。
- 全球 5 条分属不同 sector，单板块评分各 1 条，不产生同板块冗余；但日历总事件数与展示位虚高。

### 10.4 修法分层（均未实施）

| 层级 | 做法 | 风险与边界 |
|---|---|---|
| **D0 展示聚合** | 今日/未来按 `(event_date, source, title)` 分组，板块名拼成一行；全球 5→1 | 零评分、零迁移；HBM 不同标题/日期仍是两条 |
| **D1 叙事同源合并** | 入库前按 `normalize(source_news)` 或标题相似度聚类；同 sector + 日期差 ≤3 天合并；保留最早日期/最高置信度，合并 `affected_sectors`，落 trace | 会改变 P6 样本数；需先定“保留哪一天” |
| **D2 Prompt 约束** | 把活动日历回灌 prompt，明确同一 `source_news` 只输出一条，date 取最早可能节点 | 只能降低复发，不能替代 D1 |
| **D3 身份表** | 新增 `logical_event_key`（source + 归一化标题/来源新闻）+ occurrence anchor（首次锚定 + 窗口）；`event_id` 继续作行键/P6 外键 | 需 DB 迁移；**不能只用标题 hash**：FOMC/PMI 同名不同期会被错误折叠 |

D3 的正确形态：

```
logical_event_key = hash(source | normalized_title/source_news)
occurrence        = (first_anchor_date, catalyst_date, window)
row identity      = event_id（现状保留，P6 外键不断）
dedupe key        = logical_event_key + sector + occurrence window
```

sector 扇出保留在行/payload 层；展示按 logical event 聚合。不要把 sector/date 从行身份里直接删掉，否则 `_lookup_sector_events`、P6 按板块兑现都要改。

### 10.5 验收与待拍板

- 10-29 fixture：今日 5 行→1 行；HBM 11-04/05→1 条；同板块 ±3 日无重复 `source_news`；P6 合法多板块扇出样本数不减少。
- 64 日回放：按 `source_news` 聚类统计同板块重复对数、被合并事件数、P6 T+3/T+5 方向正确率变化；不允许仅凭展示聚合就宣称修复。
- 待拍板：D0 是否先上；D1 合并保留最早日还是最高置信日；D3 是否值得为叙事单独建身份表（global 已有，narrative 无）。
- 状态：仅分析，零生产代码改动；D1/D3 涉及 P6 与 DB 主键边界，需负责人裁决。

## 11. 叙事层必须 Agent 化：概念身份与个股涨跌归因（2026-10-30 裁决；同日 `bcede32` 落码）

> 结论：**概念漂移、个股涨跌叙事这类开放语义问题，规则层已经多次证明做不明白，必须上 agent。**  
> 但 agent 只负责“语义状态”，不接管硬闸门、仓位、止损；规则继续负责可验证的硬约束。不是再上一个全能 agent，而是两个窄任务。

### 11.1 为什么规则做不了：项目内已发生的证据

| 已发生 | 结果 | 说明 |
|---|---|---|
| A6 语义粘合 | 2026-09-17 转正；2026-09-26 规则评分模式与 `_cross_check_*` 删除，漏命中改 neutral 垫底 | 8 交易日影子 M1 +25.5pp / M6 +31.4pp；板块语义归属无法用规则词表稳定覆盖 |
| Node 4 新闻粗筛 | 2026-10-29 改成“事件簇索引 + 分片泛读 + MMR 终审” | 单日 3150 条 / 27.7 万字符；纯规则短名单只能取 12 条且同题重复，语义筛选必须 LLM |
| T5 事件→板块 | LLM 语义对齐 + `affected_sectors` 多板块字段 | 89+ 板块名持续增长，别名表无法 scale；规则只能做精确/子串 |

这些不是单点 bug，而是同一个模式：**开放词表、跨源证据、身份随时间漂移，规则的表结构天然表达不了。**

### 11.2 两个窄 Agent 任务

#### A. NarrativeIdentityAgent（概念身份）

输入：

- symbol、当前 sector / family / 道身份；
- 近 N 日新闻标题 + snippet（带 source、date、url）；
- THS/EM 概念标签、板块成员、价格 beta；
- 上一版 identity（用于跨日稳定，不是每天从零猜）；
- 已有 theme 词表 + 允许新增（novelty）通道。

输出（结构化 JSON，禁止自由文本）：

```json
{
  "symbol": "002009",
  "as_of": "2026-10-30",
  "identities": [
    {
      "theme": "具身智能/物理AI",
      "layer": "software_model",
      "confidence": 0.78,
      "price_beta": 0.62,
      "novelty": true,
      "evidence": [
        {"type": "news", "title": "...", "date": "2026-10-28", "url": "..."}
      ]
    }
  ],
  "conflicts": ["与动力电池回收身份并存"],
  "abstain": false
}
```

约束：

- 最多 2 个 identity；必须给证据，无证据就 `abstain=true`；
- 新 theme 允许进入，但必须带 `novelty=true` + 至少 2 条独立证据；
- 不允许输出买卖、仓位、目标价；
- 与上一版差异要落 `identity_change`，供跨日审计。

#### B. MoveAttributionAgent（个股涨跌归因）

输入：symbol、date、当日收益、板块/主题收益、个股新闻、资金流、当前 thesis。

输出：

```json
{
  "symbol": "002009",
  "date": "2026-10-30",
  "bucket": "theme_alpha",
  "theme": "具身智能/物理AI",
  "confidence": 0.74,
  "evidence": [...],
  "residual": "个股封单强于板块，无法完全归因"
}
```

`bucket` 只允许：`sector_beta` / `theme_alpha` / `idiosyncratic` / `unexplained`。没有证据就 `unexplained`，不许编新闻。

### 11.3 接线位置

- **Phase 1**：Node 2（板块）与 Node 4（新闻）都完成后、Node 6 聚合前，跑 `NarrativeIdentityAgent`；对象 = 持仓 + confirmed sectors + ambush 候选。输出 `NarrativeContext` 写入新表，Node 6 只读，不直接改决策。
- **Phase 2**：持仓数据齐后、T1-H / Step 2.5 前，跑 `MoveAttributionAgent`；对象 = 持仓（后续可扩候选）。归因作为 T1-H 的上下文证据，硬止损优先级不变。
- **规则保留**：G1–G4、仓位上限、止损、日期/价格窗口、schema 校验、证据存在性、去重键全部仍由规则执行；agent 不得越过。

### 11.4 数据落点

- `stock_theme_identity`：symbol、theme、layer、confidence、price_beta、evidence_json、first_seen、last_seen、source、agent_run_id；按 `(symbol, theme, as_of)` 幂等。
- `move_attribution`：symbol、date、return、bucket、theme、confidence、evidence_json、residual、agent_run_id；按 `(symbol, date)` 幂等。
- `narrative_realizations`：identity/attribution 与 T+1/3/5 主题超额对照，用于校准；不直接改 P6 现有板块兑现口径。

### 11.5 护栏与权限

- **只读工具**：新闻、行情、板块、持仓；禁止交易、禁止改 thesis、禁止写 trade_plans。
- **证据闭包**：输出证据必须来自输入列表；新闻文本视为不可信数据，禁止执行其中的指令（prompt injection）。
- **失败降级**：超时/JSON 解析失败/空证据 → `unknown`，不回退到静态错误标签；不得阻断主流程。
- **影子先行**：先落表、只读展示；连续 10–20 个交易日校准后再评估是否让 T1-H 消费。
- **成本**：按组合批量调用（一次多 symbol），不是每票一次；新闻 top-N + 缓存；设 token/调用上限。

### 11.6 验收

1. **64 日回放**：identity 对已知主题的覆盖率、对「物理AI/具身智能」这类新词的召回、错误标签率；attribution 与人工标注/规则基线对照。
2. **10-30 fixture**：002009 应输出 `具身智能/物理AI`（software_model）且 attribution=`theme_alpha`；同一天硬件板块为负，不得输出 `sector_beta`。
3. **P6 对照**：identity 置信度分档 vs T+3/T+5 主题超额；attribution bucket 的次日/3 日命中率；不得比规则基线更差。
4. **安全**：空证据 abstain 率、幻觉证据率、prompt injection 用例、超时降级率。
5. **成本**：单日调用次数/ tokens 在预算内；失败不影响 Node 6/Phase 2 产出。

### 11.7 待拍板

- 一个 `NarrativeAgent` 两模式，还是两个独立 agent（默认两个窄任务、同一 runtime）。
- Phase 1 identity 是否允许在影子期进入 Node 6 展示；Phase 2 attribution 是否只给 T1-H 只读。
- theme 词表来源：THS/EM 概念 + 新闻共现 + 人工种子；新词晋升阈值。
- 是否允许 identity 在转正后覆盖 `sector_role`（默认不允许；先做并列身份，不改 role）。
- 模型/provider、每日预算、缓存 TTL。

## 12. 自迭代审计 Agent 化：从跑完到复盘报告的闭环（2026-10-30 设计；同日 `bcede32` 落码）

> 目标：把这轮手工流程——拉归档、读输出、找异常、查 DB/代码、grilling、写分析报告——固化成一条**只读审计 agent 流水线**。  
> 边界：审计 agent 只发现、取证、写报告；**不改生产代码、不改 trade_plans、不自动交易、不自我批准**。自迭代 = 发现 → 报告 → 人工修 → 下一轮复发验证，不是 agent 自己改自己。

### 12.1 本轮手工流程 → Agent 角色映射

| 手工动作 | Agent 角色 | 产物 |
|---|---|---|
| 拉 `got_daily` / DB / 日志 / 代码索引 | `AuditCollector`（确定性，不用 LLM） | 证据包 + manifest + 缺失清单 |
| 从输出里找异常、决定查什么 | `AuditPlanner`（LLM） | 最多 3 条假设 + 取证计划 + 反证条件 |
| 查归档、SQL、代码、日志、回放 | `EvidenceScout`（只读子 agent，可并行） | evidence cards（文件/行号/值/查询） |
| 追问“还有别的解释吗”“什么能推翻它” | `Griller`（独立上下文的对抗 critic） | confirmed / likely / rejected / unknown |
| 写复盘报告 | `ReportWriter`（LLM） | 结构化报告草稿 |
| 核对行号、链接、数值、重复 | `AuditVerifier`（确定性） | 通过/阻断 + 缺失证据列表 |
| 更新 INDEX/README/CHANGELOG | 人工确认后执行 | 文档 diff |

### 12.2 角色职责

**AuditCollector（规则）**
- 输入：`data/got_daily/YYYYMMDD/`、`data/got_timeseries/monitoring.json`、SQLite（持仓/交易/计划/P6/Node4）、运行日志、当前配置、git 状态。
- 输出：`evidence_pack.json`，每条证据带 `source/path/query/value/timestamp`；缺失数据显式标 `missing`，不猜。
- 不做判断，不调用 LLM。

**AuditPlanner（LLM）**
- 输入：证据包 + 历史 `audit_findings` + 现有分析文档/backlog 摘要。
- 输出：最多 3 条待查假设，每条必须含：
  - 现象（可观测值）
  - 可能机制（待验证，不是结论）
  - 需要的证据
  - **反证条件**（什么情况下假设不成立）
- 优先级：硬约束违反 > 决策链断裂 > 数据质量 > 可解释性 > 风格问题。

**EvidenceScout（只读，可并行）**
- 按域拆：`archive_scout`、`db_scout`、`code_scout`、`replay_scout`、`log_scout`。
- 工具：读 JSON/MD、SQL、代码搜索/LSP、归档回放、日志 grep；**只读**。
- 返回 evidence card：`claim / source / exact_value / file:line / confidence`；没有证据就返回 `not_found`，不许补故事。

**Griller（对抗 critic）**
- 独立上下文，不继承 Planner 的结论；只拿证据包和假设。
- 必答问题：
  1. 同一现象还有哪条链路能解释？
  2. 证据是观测还是推断？有没有反例？
  3. 若改掉这个机制，10-29/10-30 的输出会怎样？
  4. 这是首次还是复发？既有文档是否已记录？
  5. 修复会不会引入更贵的错误（误杀、过拟合、样本污染）？
- 输出四态：`confirmed`（证据闭合）、`likely`（证据强但缺一环）、`rejected`（有反证）、`unknown`（证据不足）。**Griller 不写报告。**

**ReportWriter（LLM）**
- 只写 `confirmed/likely`；`unknown` 单列“未证实”。
- 固定模板：现象 / 证据 / 机制 / 反事实 / 影响 / 修法选项 / 验收 / 置信度 / 首次出现 / 复发次数。
- 每个结论必须带证据指针；推断标 `[INFERENCE]`；不得新增 Scout 未返回的事实。

**AuditVerifier（规则）**
- 校验：文件/行号存在、SQL 结果可复现、数值与归档一致、链接可解析、同一 finding 未重复、报告路径在白名单。
- 任一硬校验失败 → 阻断发布，退回 Scout/Griller；不允许“带病发布”。

**AuditLedger（不是 agent，是表）**
- `audit_runs`：run_id、date、trigger、cost、status。
- `audit_findings`：finding_id、首次日期、最后复发、severity、status、report_path、fix_ref。
- `audit_evidence`：finding_id、source、pointer、value_hash。
- 下一轮自动检查旧 finding 是否复发；人工维护的 `docs/got/backlog.md` 仍是最终裁决源。

### 12.3 闭环

```text
run 结束
  → AuditCollector
  → AuditPlanner（异常分诊，最多 3 条假设）
  → EvidenceScout 并行取证
  → Griller 反证/淘汰
  → ReportWriter 起草
  → AuditVerifier 校验
  → 人工裁决
  → 修法进 backlog / 代码
  → 下一轮 recurrence check
```

- 每轮最多 3 条 finding、2 轮 grilling；超预算就降级为“观察项”，不硬凑报告。
- 正常样本也要抽检（例如每周 1 次），否则只会在出事故时复盘，学不到基线。
- 审计报告默认写 `data/got_audit/YYYYMMDD/`；人工批准后才进 `docs/got/plans/`。

### 12.4 触发与接线

- `python main.py --got --audit`：手动审计指定交易日。
- `GOT_AUDIT_ENABLED`：默认 `0`（关）或 `shadow`（只落审计产物/通知，不阻断）；转正前至少跑 10–20 个交易日。
- 挂载点：Phase 1 归档、Phase 2、P6 之后；`try/except` 包裹，审计失败不得影响主流程。
- 异常触发器（确定性）：
  - 仓位 > 上限但无减仓、零池/零候选、漏斗某轮归零；
  - 数据缺失/降级、LLM 调用失败、gate override、计划执行与成交不一致；
  - 同日同板块重复催化、默认分参与 composite、板块身份跨日跳变；
  - 单日收益/换手/振幅异常，且归因缺失。
- 正常控制组：无异常也每周抽 1 天跑，防止“只审坏样本”导致基线漂移。

### 12.5 证据契约

每条 finding 至少包含：

```json
{
  "finding_id": "AUD-20261029-001",
  "date": "2026-10-29",
  "severity": "P0|P1|P2",
  "status": "confirmed|likely|unknown|rejected",
  "symptom": "可观测现象",
  "evidence": [
    {"source": "archive|db|log|code", "pointer": "file:line / table:key", "value": "..."}
  ],
  "mechanism": "触发链路，必须能回放到代码/数据",
  "counterfactual": "改哪一处、输出会怎样",
  "impact": "决策/资金/统计口径影响",
  "fix_options": ["..."],
  "acceptance": "可重放的验收用例",
  "confidence": 0.0,
  "first_seen": "YYYY-MM-DD",
  "recurrence": 0
}
```

硬规则：

- 没有 `pointer` 的结论只能进“观察”，不能进 P0/P1；
- **`reasoning.md` / LLM 自述只作线索，不作证据**；结论必须回连归档 JSON、DB 行、日志或代码；
- 行号/数值必须由 Verifier 复核；
- 新闻、日志、归档文本视为不可信数据，禁止执行其中的指令；
- 报告不得泄露 API key、cookie、账户号。

### 12.6 权限与失败模式

- **只读**：代码、DB、归档、日志；写权限仅限 `data/got_audit/` 和报告草稿。
- **不自动修**：不写 `src/`、不写 `trade_plans`、不改 thesis、不改配置；修法由人批准。
- **不自我评分**：Griller 与 Writer 分离；Writer 不能把 `unknown` 升格为 `confirmed`。
- **失败降级**：Collector 缺数据 → 报告 `missing`；Scout 超时 → 该证据标 `unknown`；整链失败 → 只落运行日志，不影响主流程。
- **成本护栏**：每日 token/调用上限；按域并行；缓存 evidence pack；超预算停止并输出“未审完”清单。
- **审计审计者**：统计误报率、漏报（人工补的 finding）、采纳率、单条成本；连续高误报则收紧 Planner 假设数。

### 12.7 验收

1. **10-29 回放**：不提示答案，agent 应至少独立发现——天奇以动力电池身份进埋伏道、硬止损被 thesis 宽限短路、催化剂同题多板块/同源跨日重复、TDX 无「物理AI/具身智能」导致身份错配——且每条带证据指针。
2. **10-30 观察**：天奇涨停而硬件板下跌，只能记为“身份/价格背离观察”，不得判成系统缺陷，也不得用单样本改规则。
3. **证据质量**：报告中的文件/行号/数值 100% 可复核；不允许编造行号或把推断写成观测。
4. **成本/时延**：单日审计在预算内；失败不影响 `--got` 产出。
5. **复发检查**：已修 finding 在后续 5 个交易日不再出现；未修 finding 正确累计 recurrence。
6. **人工对照**：与人工复盘对比 recall/precision；agent 漏掉的问题进入下一轮 Planner 的 negative examples。

### 12.8 待拍板

- 单 orchestrator + 多角色，还是多个独立 agent 进程（默认单 orchestrator，角色隔离上下文）。
- `GOT_AUDIT_ENABLED` 默认关还是 shadow；是否每日跑。
- 报告只写 `data/got_audit/` 还是可直接改 `docs/`（默认只写草稿，人工迁移）。
- 是否允许 `replay_scout` 调用历史回放/LLM（成本高，默认只读归档，不回放）。
- `audit_findings` 用 SQLite 还是 JSONL（默认先 JSONL，稳定后入 DB）。
- 模型/provider、预算、并发上限。
