## P0 · Run 2 glue 硬失败崩溃（决策 Q1=B）

### 事实链（三次运行对照）

| 运行 | 时间 | 结果 | glue 产物 |

| Run 3 | 14:38 | 成功（磁盘现档） | 37 关系/30 强度/30 家族，23KB，status=ok |

1. 单次 LLM 调用（14:37:17，40s，200 OK，零重试）relations 爆量（210 条 vs 正常 16-37）吃光 `max_tokens=16000` 预算（配置点 aggregator.py:1095-1102）→ strengths 残缺、families 整段截丢（0/31）；
2. `_parse_glue_response` 截断抢救（aggregator.py:932-944）补活残 JSON，制造"解析成功"假象；
3. S3 覆盖检测（:1018-1033）发现 0/31 → degraded=31 → 闸门拦截。
4. `finish_reason` 全程无记录（debug 日志 0 次命中）——失败原因不可观测。代码级原因：底层封装 `_call_llm_async`（aggregator.py:4886）经 `adapter.call_text(...)` 只回文本，节点层无处取 finish_reason——修复 1 需下沉到 LLM 适配层。

### 用户决策原文

> "没有降级，原有的规则模式明天就删除了，保留硬失败，要做的事确认失败原因做处理，而不是没完没了的降级。"

（Q1 选项 A 重试+降级放行 / C 写盘后置均否决。）

### 修复项

1. **finish_reason 记录**：LLM 响应记录 `finish_reason`；`length`（截断）判定为失败，不走截断抢救；
2. **输出调序**：`_build_glue_prompt`（函数 aggregator.py:787，输出格式段 :895-908）将 strengths/families 放前、relations 最后——爆量段截断时牺牲的是冗余信息而非核心结构；
3. **失败写盘不覆盖**：`_save_glue_result`（:1169-1201）status≠ok 时写 `agent_glue_degraded_HHMM.json`，不覆盖主文件。**连带改动（必做，否则写了也白写）**：`archive_daily_run` 原子替换只搬运 `agent_glue.json` 与 `_replay/`（archive.py:109-116），其余文件随 `.old` 目录被 `shutil.rmtree` 销毁（:157/:161）——degraded 文件会在下一次成功归档时被删除（与 Run 2 物证被 Run 3 抹掉同因）。需二选一：glob 搬运 `agent_glue_degraded_*.json` 进 tmp，或写到归档目录之外的取证子目录（如 `_forensics/`）。另 `HHMM` 时间戳命名游离于 Q6-A 按日去重契约之外，需在文档中声明为 forensics 例外；

### 决策：A — 新入保护 + 升格临近豁免
